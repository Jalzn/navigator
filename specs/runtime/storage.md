# Storage and artifacts

## Store abstraction

The runtime depends on a small async `Store` protocol. It does not know consumer
directories or names such as `.factory` and `.laboratory`. The caller supplies a
store instance/configuration.

The initial durable implementation is `SQLiteStore`; `MemoryStore` is used for
contract and unit tests. JSON plus `filelock` was considered, but durable FIFO,
leases, acknowledgement, compare-and-swap, and multi-process deduplication would
reimplement transactional database behavior.

## SQLiteStore

`SQLiteStore` uses `aiosqlite`. SQLite provides cross-platform transactions,
unique constraints, indexes, and crash recovery without a broker or server.

Version 1 tables:

```text
runtime_meta
sessions
agents
operations
messages
events
artifacts
idempotency
context_checkpoints
approvals
```

Campaigns are Agent rows with `role = campaign`; they do not require a parallel
domain table unless later query needs justify one.

## Transactional invariants

- State rows have an integer `revision` for optimistic compare-and-swap.
- Parent rows must exist before child insertion.
- Each Agent records its template ID for audit and reconstruction within the
  current compatible consumer version.
- Parent/child/session relationships are immutable after start.
- Session ownership is a bounded renewable lease, never a permanent active flag.
- Only the current unexpired lease owner may mutate a live Session.
- Message sequence allocation and insertion happen in one transaction.
- Only one active operation is permitted per Agent, enforced by data constraints
  where SQLite supports it and transaction checks otherwise.
- An operation has at most one unresolved waiting-message reference. Creating a
  `question`/`blocked` wait and persisting its message is atomic; resolving it
  with the parent's correlated reply is also atomic.
- Leasing a message is atomic.
- Acknowledgement and durable result are committed together.
- Idempotency keys are unique within their declared scope.
- Approval request, decision, expiry, and consumption share one lifecycle row.
- A grant use is atomically consumed with the authorized operation intent; two
  consumers cannot spend it concurrently. Events audit individual uses.
- Events describing state changes are inserted in the same transaction as the
  state change; they are an audit trail, not the sole source of truth.

Version 1 begins with SQLite's rollback journal because one Runtime owns the
write connection. `foreign_keys` is enabled, busy timeouts are bounded, and
mutations use short `BEGIN IMMEDIATE` transactions. WAL is adopted only if
cross-platform multi-process measurements demonstrate a real need. Transactions
never wrap a Pi process start, WebSocket operation, or filesystem write.

Timestamps are UTC Unix milliseconds, IDs are UUID4 text with readable type
prefixes, structured JSON is canonical and Pydantic-validated, and mutable state
rows use integer revisions for compare-and-swap. Complex triggers and an ORM are
not used.

## Schema migration

`runtime_meta` contains the single current schema version and database identity.
Migrations are ordered, transactional, forward-only functions shipped with the
package. Unknown newer
versions fail closed. Automatic destructive migrations are forbidden.

Pydantic validates structured JSON columns and public models. SQL constraints
enforce identity and concurrency invariants.

## MemoryStore

`MemoryStore` implements the same behavioral contract, including revisions,
leases, and uniqueness. It is not a simplified fake that silently omits
concurrency rules. Store contract tests run against both implementations.

See `store-contract.md` for table responsibilities and atomic Store operations.

## Artifacts

Large outputs remain outside SQLite:

```text
<runtime-data>/
  runtime.db
  artifacts/
    <session-id>/
      <artifact-id>
```

The database stores:

- artifact ID;
- owning session/agent/operation;
- relative path;
- byte size;
- media type;
- cryptographic hash;
- creation and retention timestamps.

Artifact paths are generated by the store, never supplied as arbitrary absolute
paths. Writes are bounded, atomic, no-follow, and verified before publication.
Consumers receive references, not filesystem authority.

## Retention and quotas

Closing a Campaign does not delete it. Durable Campaigns, messages, results,
events, checkpoints, and final artifacts remain until the user explicitly
authorizes deletion through the consumer interface. Temporary unreferenced
artifacts may expire after a configured TTL.

```python
RetentionPolicy(
    max_store_bytes=1_000_000_000,
    max_artifact_bytes=10_000_000_000,
    temporary_ttl=86_400,
    auto_delete_temporary=True,
    auto_delete_history=False,
)
```

Approaching quota produces a Coordinator-visible event. At the hard limit,
large writes fail cleanly instead of deleting history. Permanent deletion
requires an exact Campaign ID, expected revision, and native user confirmation
at the consumer boundary. Export-before-delete must be supported.

## Backup and portability

SQLite backup APIs can produce consistent snapshots. Filesystem copy of a live
database is not the documented backup method. Paths and serialized timestamps
must remain portable across macOS, Linux, and Windows.
